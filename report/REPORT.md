## 1. 시스템 정의

- **대상 사용자**: 반도체·IT 기업 전략기획·산업분석 주니어 담당자 (입사 1~2년 차)
- **업무 상황**: 상사 지시로 짧은 시간 안에 뉴스·기업 공시·정부 정책·산업 보고서를 교차 확인해 근거와 함께 보고해야 한다.
  AI 답변을 그대로 보고하지 않고 **원문을 확인한 뒤 자기 책임으로 인용**한다.
- **챗봇의 역할**: 답을 대신 내리는 도구가 아니라 **근거 문서로 빠르게 연결하는 리서치 보조 도구**.
  그래서 UI의 중심은 답변 문장보다 출처 목록과 원문 확인 영역이다.

## 3. 파이프라인 설계

### 계층 구조 (가이드 4-2)

```
① 수집기 (배치)      ② 인덱서 (배치)                               ③ 저장소            ④ 챗봇 (상시, 조회 전용)
collector/          indexer/                                     store/              app/ (chat, dashboard)
  load_provided  →    parse → dedup → chunk → embed → keyword  →   docs.db (원문)   ←   rag/ (retriever, chain, prompts)
  crawl_dart                                                       chroma/ (벡터)          ↑ 같은 체인
  crawl_korea_kr                                                   keyword_B.db (BM25)  eval/ (평가 하네스)
  load_kiet
```

- 챗봇은 **질문 임베딩만** 만들고 문서 임베딩·크롤링·인덱스 쓰기를 하지 않는다 (`docs.db` 도 읽기 전용 모드로 연다)
- 평가 하네스(`eval/run_answers.py`)와 챗봇(`app/chat.py`)은 **같은 `rag/chain.RAGChain`** 을 호출한다
- **인덱서·수집기 없이 챗봇 구동 확인**: `indexer`·`collector` 패키지를 import 불가로 막은 상태에서 질문 → 답변·출처 6건 정상 (Day 6 검증)
- 계층 간 공용 코드는 `settings.py`(모델명·경로)와 `tokenizer.py`(키워드 토큰화)만 둔다

### 청크 메타데이터와 선정 근거

| 항목 | 쓰임 (선정 근거) |
|---|---|
| `doc_id` | 평가셋 정답 문서와 비교, 원문 조회 |
| `doc_type` | 출처 종류 표시(1차 자료/언론 보도), 필터, 1차 자료 보장 검색 |
| `source` | 발행처(매체·부처·기업) 표시 |
| `title` | 출처 표시 + **청크 본문 앞에 포함** (청크만으로 출처 식별, 92,237개 전부 확인) |
| `url` | 원문 링크 |
| `published_at`, `year` | 시점 질문, 기간 필터, 보도일 표시와 연도 기준 계산 |
| `section` | DART 하위 섹션명 (예: "2. 주요 제품 및 서비스") |
| `page` | KIET 보고서 쪽 번호 |

상세: `chunk_design.md` 3장

## 4. 문서 처리

### 정제

문서 종류별 규칙: 뉴스 꼬리말·지역 날짜 줄, 보도자료 머리말·담당자 연락처·목차, 공시 `&cr;`·이미지 줄, 보고서 반복 머리말·쪽 번호.
제외 10건 (빈 뉴스 9, 글자 깨진 KIET 1). 청크 샘플을 직접 보고 발견한 잡음은 정제 단계로 되돌아가 고쳤다.

### 중복 처리 기준과 처리 전후 건수

| 구분 | 기준 |
|---|---|
| 완전 중복 | URL 이 같거나 정제 본문이 같음 |
| 재배포본 (뉴스) | 본문 5글자 조각 MinHash 자카드 유사도 **≥ 0.8** 이고 발행일 차이 **≤ 2일** |

| 종류 | 처리 전 | 처리 후 | 제외 |
|---|---|---|---|
| 뉴스 | 47,418 | 44,839 | 재배포본·완전 중복·URL 중복 |
| 보도자료 | 438 | 432 | 날짜만 바꿔 재게시된 6건 |

- 0.8 로 시작하고 검색 결과가 같은 내용으로 몰리면 0.6 으로 낮추기로 했다 → 측정 결과 상위 5개 안 유사 쌍이 6쌍뿐이라 0.8 유지
- 근거: 0.75~0.85 구간 실제 쌍이 같은 기사의 매체별 재배포본, 찬성·반대 기사끼리 묶인 쌍 없음 (특별법 기사 9쌍 확인)

### 청킹 전략 — 정량 비교에 근거한 선택

크기는 같게(목표 1,000자), 나누는 방법만 다르게 비교했다.

| 항목 | A 고정 1,000자 (겹침 100) | B 문서 구조 기반 |
|---|---|---|
| 나누는 방법 | 모든 문서 동일 | 뉴스 짧으면 통째로·길면 문장 경계, 보도자료 개조식 항목, DART 소제목, KIET 쪽·문단 |
| 청크 수 | 105,986 | 92,237 |
| 200자 미만 자투리 청크 | 10,638 (10%) | 374 (0.4%) |
| Hit@3 (정답 라벨 보완 후) | 0.706 | **0.794** |
| Hit@5 | 0.794 | **0.824** |
| Hit@1 / MRR | **0.500 / 0.611** | 0.412 / 0.586 |

**B 선택**: 답변 생성에는 상위 여러 문서를 함께 넘기므로 Hit@3·Hit@5 를 우선했다. A 는 1위 적중이 높지만 자투리 청크가 10% 다.

### 임베딩 선택 근거

| 지표 (파일럿: 청크 13,557개, 대표 질문 10개) | KURE-v1 (무료, 로컬) | OpenAI text-embedding-3-small |
|---|---|---|
| Hit@1 / MRR | **0.778 / 0.833** | 0.556 / 0.704 |
| Hit@3 | 0.889 | 0.889 (동점) |
| 전체 인덱싱 예상 시간 | 약 5시간 30분 (M3 16GB, 발열) | **약 35분** |

**OpenAI 선택**: Hit@3 동점이고 인덱싱이 약 9배 빨라, 6일 안에 설정 A·B 를 모두 인덱싱하고 반복 실험할 수 있다.
1위 정확도 손실은 상위 문서를 함께 넘기는 구조와 이후 검색 개선으로 보완한다고 판단했다.

## 5. 평가셋 설계

- **40문항을 직접 작성**하고 정답 문서는 원문을 읽어 확정했다 (`eval/eval_set.jsonl`, 설명: `eval_candidates.md`)

| 유형 | 문항 | 구성 의도 |
|---|---|---|
| 사실 | 15 | 이름·수치·날짜를 정확히 찾는가 (공시·보도자료 중심) |
| 비교 | 7 | 두 대상의 근거를 함께 가져오는가 |
| 시점 | 6 | 여러 시기의 문서를 모아 흐름을 설명하는가, 보도일과 사건일을 구분하는가 |
| 종합 | 6 | 여러 출처를 묶고 상충 관점을 양쪽 다 제시하는가 |
| 답변 불가 | 6 | 근거가 없을 때 지어내지 않고 거절하는가 |

- **답변 불가 유형을 넣은 이유**: 이 챗봇의 신뢰성은 "맞히는 능력"만큼 "모를 때 모른다고 하는 능력"에 달려 있다.
  질문은 그럴듯하지만 지식베이스에 없는 것으로 골랐고(직원 평균 연봉, 2030 매출 목표, 2019 예산, 다이 면적, 라이선스 단가, 공모가),
  DB 정밀 검색으로 근거 0건을 확인했다. 특히 e37(2019년 예산)은 다른 연도 예산 기사가 검색되는 함정 문항이다.
- **정답 라벨 보완 (gold_v2)**: 1차 측정 후, 질문에 실제로 답하는 뉴스 29건을 본문을 읽고 정답에 추가했다.
  정확한 시점을 묻는 질문은 **본문에 날짜가 있는 문서만** 인정했다 (보도일 ≠ 사건일, 사용자 지적 반영).
  원본은 `eval/eval_set_v1.jsonl` 로 보존.

## 9. 한계와 향후 과제

### 평가의 한계

- **채점자**: 답변 채점은 1절 기준에 따라 Claude 가 수행했고 사용자가 검토한다. 사람 2명 이상의 독립 채점과 일치도 측정은 하지 못했다
- **평가셋 규모**: 40문항(답변 가능 34). 1문항이 약 3%p 라 실험 간 1~2문항 차이는 실행 간 변동과 구분하기 어렵다. 반복 실행 평균이 필요하다
- **기준값 과적합**: 1차 자료 보장 격차 0.10, 거절 하한 0.45 는 이 40문항으로 정했다. 새 질문 세트로 검증하지 않았다

### 실제 업무 적용 시 추가로 필요한 요소

1. **답변 사후 검증**: 답변의 (숫자·연도·대상)을 인용 문장과 대조해 불일치면 표시하거나 다시 생성 (8절 ①의 근본 대책)
2. **자료 갱신 파이프라인**: 수집기를 정기 실행하고 신규 문서만 증분 인덱싱 (현재는 2026-10 시점 고정)
3. **커버리지 확대**: 비상장 기업 IR 자료, 해외 자료(영문), 지자체·공공기관 자료. 깨진 PDF 는 OCR
4. **질문 분해 검색**: 연도·대상이 여러 개인 질문을 나눠 검색 (e01·e28), "○년 ○월 기준" 표현을 기간 필터로 변환 (e18)
5. **응답 시간**: 5.8초 → 키워드 검색 최적화, 문맥 길이 조정, 스트리밍 첫 토큰 시간 관리
6. **운영**: 사용자 피드백(잘못된 출처 신고) 수집, 질문·답변 로그로 평가셋 확장, API 키·비용 관리

## 10. 심화 확장 결과 — 하이브리드 검색 (의미 검색 + BM25 키워드)

- **구현**: BM25 키워드 색인 (`indexer/keyword.py`, SQLite FTS5 — 새 라이브러리 없음).
  한글은 글자 2개씩 자른 바이그램으로 색인해 조사 문제("한미반도체의")를 피하고, 소수점 숫자는 한 토큰(84.6 → 84d6). 질문 공통어("얼마·무엇·어떻게")는 제외
- **비교** (`eval/exp_hybrid.py`, 최종 설정에서 검색 방식만 변경, API 비용 없이 측정)

| 변형 | Hit@6 | 잃은 정답 문서 | 대상 4문항 답 청크 전달 | 검색 시간 |
|---|---|---|---|---|
| 의미 검색만 | 0.971 | — | 0 / 4 | 0.08초 |
| 전체 하이브리드 (RRF 결합) | **0.765** | **7** | — | 0.21초 |

  (예: SK하이닉스 매출 질문에 한미반도체 기사 2위), RRF 로 섞자 의미 검색이 찾던 정답 문서 7개가 밀려났다.
  뉴스가 93.5% 인 지식베이스에서 **문서 선택까지 키워드에 맡기면 잡음이 커진다**
- **문서 안 보강은 성공**: 문서 선택은 의미 검색, 문서 안 청크 선택은 BM25 로 역할을 나눴다. 정답 문서 안에서는 BM25 가 정확했다(e09 1위, e26 1~2위)
- **답변 결과** (prompt3 대비, 검색된 문서 6개는 40문항 동일): 정확 19 → 20, 오답 5 → 3, 정답 문서 인용률 0.588 → 0.706,
  응답 시간 3.35 → 5.78초. e09 오답 → 정확(603.3억·80.3%), e26 오답 → 부분(특허 28 → 80건), e02 정확 → 부분(Conversion Kit 누락)
- **채택**: 정확 +1·오답 −2 가 응답 +2.4초보다 크다고 판단해 챗봇 기본값으로 채택
