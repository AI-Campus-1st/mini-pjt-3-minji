## 1부. 임베딩 모델 선택 — text-embedding-3-small (OpenAI)

> 결정일: 2026-11-04 (Day 2) · 리포트 4항 "임베딩 선택 근거"의 근거 자료
> 실험 코드: `eval/pilot_build.py`, `eval/pilot_embedding.py` · 결과: `eval/results/pilot_embedding_*.json`

### 결론

**OpenAI text-embedding-3-small**을 사용한다.
우리 데이터로 비교한 결과 KURE-v1이 1위 정확도(Hit@1)와 MRR에서 앞섰지만, Hit@3은 같았고,
전체 인덱싱 시간이 약 9배(5시간 30분 vs 35분)라 6일 일정 안에 반복 실험을 할 수 없다고 판단했다.

### 1. 후보 선정

| 후보 | 선정 이유 |
|---|---|
| nlpai-lab/KURE-v1 | 가이드 참고 링크(한국어 검색 리더보드)에서 1위 (Recall@3 0.687), 무료, 로컬 실행 |
| OpenAI text-embedding-3-small | 교육 과정 제공 API 키, 저렴(100만 토큰당 $0.02), 서버 계산으로 빠름 |

리더보드는 위키백과·의료·법률 등 **다른 데이터셋** 결과이므로, 우리 데이터로 직접 비교했다.

### 2. 실험 설계 (파일럿)

| 항목 | 내용 |
|---|---|
| 문서 | 3,612건 — 정답 문서 + DART·KIET·보도자료 전부 + 무작위 뉴스 3,000건 (seed 42) |
| 청크 | 13,557개, 1,203만 자 (전체 지식베이스의 약 15%) — 제목 + 본문 1,000자 창, 겹침 100자 |
| 질문 | 대표 질문 10개 (답변 가능 9 + 답변 불가 1) |
| 정답 | 제목·본문 규칙으로 고른 **근사 정답** (본 평가셋은 원문을 읽고 따로 확정) |
| 지표 | 문서 단위 Hit@1·3·5, MRR(상위 10위), 인덱싱 시간, 질문 임베딩 시간 |
| 환경 | MacBook Air M3 16GB (KURE-v1은 MPS 가속), OpenAI는 API |

#### 정답 보정 (q08)

OpenAI가 q08에서 2위로 찾은 `press_20220627_156513527` "과기정통부, 인공지능(AI) 반도체 산업 성장 지원대책 발표"는
정답에 해당하지만, 정답 선정 규칙이 '인공지능 반도체'(괄호 없음)만 찾아 누락됐다.
→ **규칙 기반 근사 정답의 한계**. 본 평가셋은 원문을 읽고 정답을 확정해야 한다는 근거로 쓴다.

### 4. 판단

| 기준 | KURE-v1 | OpenAI 3-small |
|---|---|---|
| 상위 3개 검색 (Hit@3) | 0.889 | 0.889 (동점, 보정 후) |
| 1위 정확도 (Hit@1) | **우세** (+2문항) | |
| 전체 인덱싱 1회 | 약 5시간 30분 | **약 35분** |
| 3~4회 반복 인덱싱 (청킹 비교 + 개선 실험) | 약 20시간 이상 → **일정상 불가** | 약 2~3시간 → 가능 |
| 실행 환경 부담 | 팬 없는 맥북에어에서 장시간 발열, 스로틀링으로 추가 지연 가능 | 없음 |

- RAG는 상위 k개(보통 3~5개)를 함께 생성 모델에 넘기므로, Hit@3 동점이면 답변 품질 차이는 제한적일 것으로 본다.
- 1위 정확도 차이는 Day 5 개선 단계에서 **Reranker(심화 확장)** 등 검색 단계 개선으로 보완을 시도할 수 있다.
- 가이드 4-4: "임베딩 모델을 변경하는 것보다 청킹을 조정하는 것이 더 효과적인 경우가 많다" → 반복 실험이 가능한 모델을 택하는 것이 개선 루프에 유리하다.

### 5. 후속 과제와 관찰

| 관찰 | 의미 | 반영 시점 |
|---|---|---|
| q05는 두 모델 모두 실패 (상위가 뉴스로 채워짐) | 임베딩이 아니라 **문서 종류·연도 구분** 문제 → 메타데이터 필터, 청크 제목 구성 개선 대상 | Day 3~5 |
| 답변 불가 문항의 1위 유사도가 모델마다 다름 (0.72 vs 0.51) | 거절 임계값은 **선택한 모델로 따로 측정**해서 정해야 함 | Day 4 |
| 질문 9개 기준 결과 | 표본이 작아 1문항 차이가 크게 보임 → 본 평가셋(30~50문항)으로 재확인 | Day 3 |

### 6. 실험의 한계

- 질문 9개, 규칙 기반 근사 정답이라 결과의 신뢰구간이 넓다.
- 파일럿은 전체의 약 15% 분량이며, 전체 인덱싱 시간은 처리 속도로 단순 추정했다. KURE-v1은 발열로 속도가 떨어졌을 수 있다.
- 청킹은 파일럿 전용 단순 방식(1,000자 창)이다. 청킹 방식이 바뀌면 두 모델의 차이도 달라질 수 있다.

## 2부. 중복 처리 기준 — 유사도 0.8 + 발행일 2일 이내 (1차)

> 결정일: 2026-11-04 (Day 2) · 리포트 4항 "중복 처리 기준과 처리 전후 건수"의 근거 자료
> 코드: `indexer/dedup.py` · 결과 테이블: `store/docs.db` → `dedup_map`, 실행 기록 `collect_log` (step='dedup')

### 결론

| 구분 | 기준 | 대상 |
|---|---|---|
| 완전 중복 | URL 이 같거나 정제 본문이 완전히 같음 | 모든 문서 |
| 재배포본 | 본문 5글자 조각의 자카드 유사도 **≥ 0.8**, 발행일 차이 **≤ 2일** | 뉴스 |
| 대표 선정 | 묶음에서 정제 본문이 가장 긴 문서 (같으면 먼저 발행된 문서) | |

**0.8은 1차 기준(보수적)**이다. Day 3 평가에서 검색 상위에 같은 내용이 몰리면 **0.6으로 낮춰 재측정**한다

|---|---|---|

| 0.40~0.45 | "中 반도체 디커플링 신중해야" vs "中 공급망 장악 여전" | **다른 관점** → 남겨야 함 |

- 대표 질문 9번(반도체 특별법 찬반) 관련 기사 중 0.5 이상으로 묶이는 쌍 9개를 확인: 모두 같은 발언·같은 매체 후속 기사였고, 찬성·반대 기사끼리 묶인 쌍은 없었다.
- 발행일 조건(2일)이 없으면 추가로 묶이는 쌍은 약 60~120건이며, 같은 이슈의 다른 단계 기사가 섞일 수 있어 조건을 둔다.

#### 0.8로 시작한 이유

- 0.6~0.8 구간은 표본상 같은 내용이었지만, 직접 확인한 표본 수가 적어 **다른 관점 기사가 없다고 장담할 수 없다.**
- 가이드 4-4: "서로 다른 관점의 보도까지 제거하면 상충 정보를 제시하는 기능이 성립하지 않으므로, 기준을 과도하게 설정하지 않도록 유의한다."
- 임베딩이 OpenAI(전체 인덱싱 약 35분)라 기준을 바꿔 재측정하는 부담이 작다 → **보수적으로 시작해 평가 결과로 조정**한다.

### 3. 계산 방법

- MinHash: 공백을 지운 정제 본문 앞 3,000자 → 5글자 조각 → 128개 해시의 최솟값 = 문서 지문 (seed 0)
- LSH: 지문을 32구간 × 4로 나눠, 한 구간이라도 같은 문서끼리 후보 쌍으로 모음 (후보 29,144쌍)
- 후보 쌍의 유사도 = 두 지문의 일치 비율 (자카드 유사도 추정치)
- 묶기: 기준을 넘는 쌍을 이어 묶음 생성 (A~B, B~C → A·B·C 한 묶음), 중복이 있는 묶음 1,937개

### 4. 평가셋에 주는 영향 (Day 2 평가셋 작성 시 반영)

- 중복으로 제외된 문서는 검색 대상이 아니므로, **평가셋 정답 문서(gold_doc_ids)는 keep=1 인 대표 문서로 지정**한다.
  예: `news_20241107_031726`(제외) → 대표 `news_20241106_031725`
- 기준을 0.6으로 바꾸면 대표 문서가 달라질 수 있으므로, 평가 하네스는 `dedup_map.group_id` 로 정답을 대표 문서에 연결해 비교한다.

### 5. Day 3 이후 실험 계획

| 단계 | 내용 |
|---|---|
| 1차 측정 | 0.8 기준으로 인덱싱 → Hit@k, MRR + **검색 상위 5개 중 같은 묶음·같은 사건 기사가 몇 개인지** 확인 |
| 판단 | 상위 결과에 같은 내용이 반복되는 질문이 많으면 |
| 2차 측정 | `python -m indexer --only dedup --dedup-threshold 0.6` → 재인덱싱 → 재측정, 전후 비교 |

## 3부. 청킹 설계 — 설정 A(고정 길이) vs 설정 B(문서 구조 기반)

> 작성일: 2026-11-04 (Day 2) · 리포트 4항 "청킹 전략"의 근거 자료
> 코드: `indexer/chunk.py` · 결과: `store/docs.db` → `chunks` (config = A / B), 실행 기록 `collect_log` (step='chunk')
> 비교 측정(Hit@3)은 Day 3 에 진행

### 1. 비교 설계

**크기는 같게(목표 1,000자), 나누는 방법만 다르게** 두 설정을 만들었다.
결과 차이를 "나누는 방법" 하나로 설명하기 위함이다 (가이드 4-9: 한 번에 하나의 변수만 변경).
청크 크기 비교(500자 vs 1,000자)는 이긴 방법으로 Day 5에 여유가 있으면 추가한다.

| 설정 | 나누는 방법 | 청크 앞머리 |
|---|---|---|
| A 고정 길이 (기준선) | 모든 문서를 1,000자씩, 겹침 100자 | 문서 제목 |
| B 문서 구조 기반 | 문서 종류별 자연 경계에서 목표 1,000자로 묶음 | 문서 제목 + 소제목(DART) / 쪽 번호(KIET) |

#### 설정 B 의 문서 종류별 규칙 (가이드 4-4 청킹 방향 반영)

| 문서 | 데이터 특성 | 나누는 방법 |
|---|---|---|
| 뉴스 | 줄바꿈 없는 한 덩어리, 중앙값 1,322자, 43%가 1,200자 이하 | 1,200자 이하는 **기사 통째로**, 길면 **문장 경계**로 묶음 (앞 청크 마지막 문장을 겹침으로 반복) |
| 보도자료 | □ ○ ㅇ 개조식, 중앙값 4,142자 | **개조식 항목 경계**로 묶음 |
| DART | `## 1. 사업의 개요` 같은 소제목, 중앙값 2.8만 자 | **소제목 단위** → 길면 줄 경계로 묶음, 청크에 **소제목 표시** |
| KIET | 쪽 구분, 중앙값 4만 자 | **쪽 → 문단 경계**로 묶음, 청크에 **시작 쪽 번호 표시** |
