## 1. 프로젝트 목표

가이드가 요구하는 것은 "동작하는 챗봇"이 아니라 아래 질문에 **측정된 근거로 답하는 것**이다.

> "이 챗봇의 답변을 신뢰할 수 있는가. 그 판단의 근거는 무엇인가."

따라서 이 프로젝트의 결과물은 세 가지다.

| 결과물 | 내용 |
|---|---|
| 챗봇 | 출처와 함께 답하고, 근거가 없으면 거절하는 Streamlit 챗봇 |
| 평가 | 직접 만든 평가셋으로 검색 품질(Hit@k, MRR)과 답변 품질을 측정 |
| 개선 기록 | 실패 원인을 계층별로 찾고, 한 번에 하나씩 바꿔 재측정한 전후 비교 |

## 2. 사용자와 업무 상황

### 대상 사용자

**반도체·IT 기업 전략기획/산업분석 주니어 담당자** (입사 1~2년 차)

- 반도체 기초 지식은 있지만, 업계 동향을 매일 다 따라가지는 못한다.
- 상사의 지시로 짧은 시간 안에 근거 자료를 모아 보고해야 한다.
- AI가 만든 답을 그대로 보고하면 안 되고, **원문을 확인한 뒤 자기 책임으로 인용**해야 한다.

### 업무 시나리오 예시

| 상황 | 사용자가 하는 일 | 챗봇에 기대하는 것 |
|---|---|---|
| 팀장: "경쟁사 HBM 현황 정리해 와" | 삼성전자·SK하이닉스 공시와 뉴스를 비교 | 기업 공시(1차)와 언론 보도(2차)를 구분해 출처와 함께 제시 |
| 팀장: "정부 지원사업 중 신청할 만한 거 있어?" | 과기정통부·산업부 보도자료 확인 | 정책 원문(보도자료)을 근거로 사업명·대상·시기 제시 |
| 팀장: "수출규제가 우리한테 어떤 영향이야?" | 산업 보고서와 뉴스를 함께 읽기 | KIET 분석과 언론 보도를 함께, 관점 차이를 구분해 제시 |
| 사용자가 모르는 수치를 물음 | — | 자료에 없으면 **지어내지 않고 "확인할 수 없습니다"** |

### 챗봇의 역할 정의

챗봇은 답을 대신 내리는 도구가 아니라 **근거 문서로 빠르게 연결하는 리서치 보조 도구**다.
→ UI의 중심은 답변 문장보다 **출처 목록과 원문 확인 영역**이다.

| 특성 | 예시 | 시스템에 주는 요구 |

| **모두 한국어다** | — | 한국어 검색 성능이 좋은 임베딩 |

### 4-2. 소스별 상세

**① 제공 뉴스** — `collector/load_provided.py`
- 원본: 강사 제공 CSV, 키워드 "AI 반도체"·"인공지능 반도체", 120,057건
- 처리: 본문 결측 제외(→ 119,971) → **관련성 필터**(→ 47,428)
  - 필터 근거: 본문에 "AI 반도체"가 한 번도 없는 기사가 50% (증시 시황·정치 기사 등)
  - 기준: 제목에 반도체 관련어(반도체, HBM, NPU, 칩, AI 가속기, 국내 AI 반도체 스타트업명) **또는** 본문에 "AI 반도체" 2회 이상
- 남은 과제: **중복 제거** (제목·본문 앞부분 기준 약 8,400건 중복 추정, 재배포본은 더 많을 것), 기사 말미 보일러플레이트 제거
- 기간 편중: 2024년 이후가 85%

**② DART 사업보고서** — `collector/crawl_dart.py`
- 대상: 7개 기업 × 4~5년 (밸류체인별 선정)
  - 메모리: 삼성전자, SK하이닉스 / 장비: 한미반도체 / 설계 IP: 오픈엣지테크놀로지 / 설계 서비스: 가온칩스 / 기판: 삼성전기 / PCB: 이수페타시스
- 추출 범위: 사업보고서의 "II. 사업의 내용" 섹션 (하위 제목을 `## 제목`으로 보존)
- 특징: **매우 긴 문서**(1.4만~4.5만 자), 표가 `|` 구분 행으로 들어 있음

**③ 정책브리핑 보도자료** — `collector/crawl_korea_kr.py`
- 검색: "AI 반도체", "인공지능 반도체", "HBM" → 1,447건 → 소관 부처(산업부·과기정통부·기재부) 603건 → 본문 "반도체" 3회 이상 438건
- 본문: 웹페이지에 없어 **첨부 PDF**(산업부), **첨부 HWPX**(과기정통부)에서 추출
- 부처별: 산업부 337, 과기정통부 93, 기재부·재경부 8
- 특징: 보도자료 머리말(보도 시점, 배포, 담당자)이 반복됨, 수출입 동향 자료는 숫자 표 위주

**④ KIET 산업보고서** — `collector/load_kiet.py`
- 7편 (공급망, 수출통제, 대만, 시스템반도체, 한·중 경쟁력, 한·일 협력, 반도체과학법)
- 수집 방식: **수동 다운로드** (robots.txt가 파일 경로를 금지)
- 특징: **가장 긴 문서**(최대 14만 자, 177쪽), 쪽 구분자(`\f`) 보존 → 출처에 쪽 번호 표시 가능, 표가 셀 단위로 풀려 있음
- **제외 1편**: "미국의 대중 반도체 수출통제에 따른 중국의 공급망 영향과 시사점"(이슈페이퍼 2024-04, 89쪽) — PDF 글꼴 인코딩 문제로 82쪽의 텍스트가 깨져 추출 불가. OCR 복구 대신 제외를 선택(2026-11-04). 수출통제 내용은 KIET 다른 4편과 뉴스로 보완 → **인덱싱 대상 KIET 6편**

### 4-3. 접근 제약과 대응 (리포트 2항 근거)

## 5. 시스템 구조 (가이드 4-2 계층 분리)

```
① 수집기 (배치)      ② 인덱서 (배치)                     ③ 저장소           ④ 챗봇 (상시)
collector/          indexer/                           store/             app/ + rag/
  load_provided  →    parse  → dedup → chunk → embed →   docs.db (원문)  ←  retriever (질문 임베딩 → 검색)
  crawl_dart                                             chroma/ (벡터)      chain (GPT 답변 생성)
  crawl_korea_kr                                                            prompts
  load_kiet                                                                 chat / dashboard
                                                                   ↑
                                                         eval/run_eval.py (같은 rag/chain 호출)
```

| 계층 | 상태 | 실행 |
|---|---|---|
| ① 수집기 | ✅ 완료 | `python -m collector` |
| ② 인덱서 | ⏳ 오늘~내일 | `python -m indexer` |
| ③ 저장소 | `docs.db` ✅ / `chroma/` ⏳ | — |
| ④ 챗봇 | ⏳ Day 4 | `streamlit run app/main.py` |
| 평가 | ⏳ Day 2(평가셋)~Day 3(측정) | `python eval/run_eval.py` |

규칙: 챗봇은 **조회 전용** (문서 임베딩·크롤링·인덱스 쓰기 금지). 챗봇과 평가는 **같은 `rag/chain.py`** 를 호출한다.

## 8. 임베딩 모델 결정 ✅ text-embedding-3-small (상세: `report/embedding_decision.md`)

### 8-1. 임베딩이 쓰이는 곳

| 위치 | 대상 | 횟수 |
|---|---|---|
| `indexer/embed.py` | 문서 청크 전체 | 인덱싱할 때마다 (예상 **3~4회**: 청킹 설정 2개 + 개선 실험) |
| `rag/retriever.py` | 사용자 질문 | 질문마다 1회 (챗봇·평가) |

문서와 질문은 반드시 **같은 모델**이어야 하므로, 모델을 바꾸면 전체를 다시 임베딩해야 한다.

### 8-2. 이 프로젝트가 임베딩에 요구하는 것

| 요구 | 중요도 | 근거 |
|---|---|---|
| 한국어 검색 정확도 | **높음** | 과제의 핵심이 검색 품질 측정, 문서·질문 모두 한국어 |
| 고유명사 매칭 | 높음 | 기업명·제품명·정책명 질문이 많음 |
| 반복 인덱싱 속도 | **높음** | 인덱싱 3~4회 예상, 6일 일정 |
| 긴 입력 | 중간 | 청킹 후에는 조각이 짧아짐 (긴 청크 실험 시에만 중요) |
| 비용 | 낮음 | OpenAI 키는 교육 과정 제공, 로컬 모델은 무료 |

### 8-3. 후보 비교

한국어 성능 = 가이드 참고 링크인 한국어 검색 리더보드(KURE 저장소, 8개 데이터셋 평균)의 Recall@3

| 항목 | KURE-v1 (고려대) | OpenAI text-embedding-3-small | OpenAI text-embedding-3-large |
|---|---|---|---|
| 한국어 Recall@3 | **0.687 (1위)** | 리더보드에 없음 | 0.610 |
| 비용 | 무료 | 100만 토큰당 $0.02 (공용 키) | 100만 토큰당 $0.13 (공용 키) |
| 계산 위치 | 내 맥 (M3, 16GB) | OpenAI 서버 | OpenAI 서버 |
| 전체 인덱싱 시간 | ⏳ **속도 테스트 필요** | 수십 분 (추정) | 수십 분 (추정) |
| 질문 임베딩 | 매우 빠름 (로컬) | 0.1~0.5초 (네트워크) | 0.1~0.5초 |
| 설치 | PyTorch + 모델 약 2.3GB | `openai` 패키지 | `openai` 패키지 |
| 최대 입력 | 8,192토큰 | 8,191토큰 | 8,191토큰 |
| 벡터 차원 | 1,024 | 1,536 | 3,072 |
| 인터넷 | 처음 다운로드 때만 | 항상 필요 | 항상 필요 |

### 8-4. 결정 절차

```
KURE-v1 속도 테스트 (맥에서 청크 1,000개 임베딩, 약 10분)
  ├─ 전체 인덱싱 예상 1시간 이내 → KURE-v1 확정 (정확도와 반복 속도 모두 충족)
  └─ 몇 시간 이상               → OpenAI text-embedding-3-small
```

어느 쪽이든 (여유가 있으면) 부분집합으로 다른 모델과 Hit@3를 비교해 리포트의 선택 근거로 쓴다.
(가이드 4-5: "선택한 모델 자체보다 선택 근거를 기술하는 것이 중요하다")
